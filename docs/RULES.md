# Backend Development Rules & Coding Standards
## ClinIQ: Backend Code Standards & Security Rules

---

## 1. Python & FastAPI Code Standards

### 1.1 Code Style & PEP 8
* **Python Target:** Python 3.12+.
* **Type Annotations:** Strictly annotate all function arguments and return types. Use `typing` / Python 3.12 standard generics (`List`, `Dict`, `Optional`, `Union`, `Tuple`, or built-in `list[str]`, `dict[str, Any]`).
* **Defensive Settings & Type Casting:** Functions returning heterogeneous dictionary mappings (such as `load_settings()`) must explicitly specify `-> dict[str, Any]` to prevent static type checkers (Pyright/Pylance) from inferring brittle union types (`dict[str, Union[str, int]]`). When retrieving string variables from settings dictionaries for formatting or sanitization (`.strip()`), always wrap lookups defensively in `str(settings.get(key) or "")` to guarantee type safety and prevent runtime `AttributeError`.
* **Pydantic Validation:** All API request bodies and structured responses must be validated with Pydantic v2 schemas in `app/schemas/`.
* **Async / Non-Blocking:** Use `async def` for I/O bound endpoints (e.g. database access, HTTP client calls to Deepgram/OpenRouter, email dispatch). Use synchronous threads via `run_in_executor` for CPU-bound tasks (e.g. local ReportLab PDF rendering, ChromaDB embeddings).

### 1.2 Project Layout Rules
* Keep routes thin; delegate business logic to dedicated services in `app/services/` or `app/rag/`.
* Keep database queries encapsulated in models or service classes. Never write raw SQL strings inside API route definitions.
* Never instantiate heavyweight external clients (LLMs, Embeddings, DB connections) inside endpoint functions; reuse singleton instances managed in core modules.

## 2. Security & PHI Protection Rules

> [!CAUTION]
> Backend services process patient voice recordings, transcriptions, and medical records. Strict safeguards must be enforced.

1. **Credential Segregation:**
   * Never commit secrets (`DEEPGRAM_API_KEY`, `OPENROUTER_API_KEY`, `GMAIL_APP_PASSWORD`, `DATABASE_URL`, or `service_account.json`) into version control.
   * Load all secrets through Pydantic `BaseSettings` in `app/core/config.py` backed by `.env`.
2. **Path Traversal Prevention:**
   * All file download endpoints (such as `/reports/{filename}`) must sanitize inputs:
     ```python
     if "/" in filename or "\\" in filename or ".." in filename:
         raise HTTPException(status_code=400, detail="Invalid filename")
     ```
3. **Database Injection Safeguards:**
   * Always use parameterized SQLAlchemy ORM queries to eliminate SQL injection vulnerabilities.
4. **CORS Configuration:**
   * In production, configure specific allowed frontend origins in `CORSMiddleware` instead of open wildcards.

## 3. LangGraph & AI Prompting Rules

* **Deterministic Output Extraction:**
  * When prompting LLMs for structured data (entities, differential diagnoses, SOAP notes), enforce JSON schemas with temperature $\le 0.2$.
  * Always implement defensive JSON parsers (`json_utils.py`) to safely handle LLM markdown backticks (```json ... ```) and minor formatting variances.
* **Grounding & Hallucination Prevention:**
  * Every differential diagnosis candidate generated by the agent must cite specific retrieved guideline chunks or state explicit clinical reasoning grounded in the patient's symptoms.

## 4. Error Handling & Logging Rules

* **HTTP Exception Hierarchy:** Use standard FastAPI `HTTPException` with precise status codes:
  * `400 Bad Request`: Validation failure or malformed payload.
  * `401 Unauthorized`: Invalid or expired JWT / OTP.
  * `403 Forbidden`: Role mismatch (e.g. Patient accessing Admin endpoint).
  * `404 Not Found`: Visit, Doctor, or Report not found.
  * `502 Bad Gateway`: Upstream AI API (Deepgram / OpenRouter) failure with user-friendly retry message.
* **Structured Logging:**
  * Use Python's `logging` module. Never use unformatted `print()` in production code paths.
  * LangSmith tracing (`app/core/tracing.py`) should be enabled for comprehensive LLM call telemetry.
* **Symmetrical Property Serialization Rule:** In all consultation encounter and session JSON response payloads, emit both camelCase (`aiSuggestions`) and snake_case (`ai_suggestions`) for structured collections to guarantee interoperability across web and native clients.
* **Vitals Serialization & Fallback Rule:** Patient and consultation response dictionaries must never serialize `vitals: {}` as an empty object. Always provide standard adult triage baseline metrics unless specific patient triage values are present. In `PipelineService`, fallback entity generation must inspect transcript text to extract vital signs and symptoms dynamically rather than outputting empty dictionary structures.
* **CDS Tab Completeness Rule:** Audio upload and dialogue analysis endpoints must never return partial CDS intelligence where differential diagnoses, guideline medicines, confidence metrics, red flags, or follow-up questions are missing or empty. When LLM or RAG services are degraded or offline, fallback pipelines must synthesize complete condition-adaptive structures for all 5 CDS tabs with matching schema keys.
* **Database Connection URL & Dialect Normalization Rule:** PostgreSQL URLs passed to SQLAlchemy `create_engine()` must always be normalized via `get_normalized_db_url()` to explicitly include the driver dialect (`postgresql+psycopg2://`). Never leave unadorned `postgresql://` which triggers missing driver errors in SQLAlchemy 2.0+.
* **Doctor Queue Seed & Roster Consistency Rule:** All clinical specialists registered in the system must be populated in seed initialization routines (`ensure_initial_seed_data`) with active patient assignments and booked slots. Queue endpoints (`/api/scheduling/queue/{doctor_id_or_name}`) must provide fallback querying to unassigned triage patients and department patients so that newly enrolled clinicians never experience an empty dashboard.

## 5. Mandatory Documentation Synchronization Rule

Whenever making code changes, modifying schemas, refactoring services, or adding new features:
* **Always update the corresponding documentation files in `docs/`:**
  * `PRD.md`: API requirements, functional capabilities, integration targets.
  * `ARCHITECTURE.md`: Graph topology, data schemas, ER models, service connections.
  * `RULES.md`: Backend coding standards, security, error handling.
  * `KNOWLEDGE.md`: Clinical taxonomy, vector embeddings, Deepgram/LLM configs.
  * `DESIGN.md`: REST API endpoint schemas, request/response models, DB models.
  * `TASKS.md`: Task tracking, sprint completion, new backend backlog items.
  * `MEMORY.md`: Backend ADRs, environment configs, debugging runbooks.
